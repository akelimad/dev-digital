Les transactions en MySQL

Exécuter plusieurs requêtes comme un seul bloc : tout réussit, ou rien n'est enregistré.

1. Rôle d'une transaction

Par défaut, le client MySQL utilise la validation automatique (autocommit) : chaque requête INSERT, UPDATE ou DELETE est enregistrée immédiatement et on ne peut plus l'annuler. Voir la section suivante pour la gérer.

Une transaction regroupe une ou plusieurs requêtes en un seul bloc :

  • on peut annuler les modifications si quelque chose se passe mal ;
  • on garde la base dans un état cohérent : tout est fait, ou rien n'est fait.
Règle d'or : « tout ou rien ». Jamais la moitié d'une opération.

2. La validation automatique (autocommit)

Tout ce cours repose sur elle : il faut donc savoir la vérifier, la désactiver et la réactiver.

Quand l'autocommit est activé, chaque requête est une mini-transaction validée tout de suite. Impossible de l'annuler avec ROLLBACK.

ActionCommande
Vérifier l'état (1 = activée, 0 = désactivée)SELECT @@autocommit;
Désactiver pour la sessionSET autocommit = 0; ou SET autocommit = OFF;
RéactiverSET autocommit = 1; ou SET autocommit = ON;
SELECT @@autocommit;
SET autocommit = 0;
SELECT @@autocommit;
SET autocommit = 1;

Deux façons d'obtenir une transaction

START TRANSACTION (ou BEGIN)SET autocommit = 0
DuréeUne seule transaction. Après COMMIT ou ROLLBACK, l'autocommit revient.Toute la session, jusqu'à SET autocommit = 1.
Après COMMIT / ROLLBACKLes requêtes suivantes sont de nouveau validées automatiquement.Une nouvelle transaction démarre toute seule : il faut penser à valider à chaque fois.
RisqueFaible.Oublier le COMMIT : les changements restent en attente et sont perdus à la déconnexion.
Conseil : pour débuter, gardez l'autocommit activé et utilisez START TRANSACTION chaque fois que vous voulez pouvoir annuler.

3. Syntaxe

On démarre la transaction avec START TRANSACTION ou BEGIN (les deux font la même chose). Après les requêtes de modification, on termine obligatoirement par COMMIT ou ROLLBACK.

-- début de la transaction (ou BEGIN;)
START TRANSACTION;

   requête 1;
   requête 2;

-- valider
COMMIT;
-- ou, pour annuler :
ROLLBACK;
START TRANSACTION→requêtes→COMMITouROLLBACK

Exemple avec une table

-- début de la transaction
BEGIN;
INSERT INTO mytable VALUES (1, 'foo', 'bar', 'bas');
-- on voit la nouvelle ligne
SELECT * FROM mytable;
-- utiliser ROLLBACK à la place pour annuler l'opération
COMMIT;
Attention : les transactions fonctionnent avec le moteur InnoDB (le moteur par défaut). Certaines commandes valident automatiquement la transaction en cours et ne peuvent pas être annulées : CREATE, ALTER, DROP, TRUNCATE, LOCK TABLES.

4. Rôle de COMMIT et de ROLLBACK

COMMIT

Valide la transaction.

  • Tous les changements sont enregistrés définitivement.
  • Ils deviennent visibles pour les autres utilisateurs.
  • On ne peut plus revenir en arrière.

ROLLBACK

Annule la transaction.

  • Tous les changements depuis START TRANSACTION sont défaits.
  • La base revient à son état de départ.
  • C'est ce qu'on utilise en cas d'erreur.
Tant que COMMIT n'est pas exécuté, les modifications ne sont visibles que dans votre session.

5. Exemple : le virement bancaire

C'est le meilleur exemple pour comprendre une transaction : transférer 200 DH entre 2 comptes de la même banque.

Compte émetteur
n° 101
Débit −200 DH
→
Crédit +200 DH
Compte récepteur
n° 102
Le problème : le débit a réussi mais le crédit n'a pas eu lieu (problème de base de données, coupure...). Les 200 DH ont disparu : la base est dans un état incohérent.
La solution : avec une transaction, si le crédit échoue, le débit est annulé. Aucun changement dans la base.

Le schéma de la banque

TableColonnes
clientnum, nom, prenom, adr, tel
comptenum, solde, type (CC = compte courant, CE = compte épargne), num_client (clé étrangère vers client)
operationsnum, type (retrait ou versement), montant, num_compte (clé étrangère vers compte), date_o

Un virement modifie 2 comptes et ajoute 2 lignes dans operations (un retrait et un versement) : soit 4 requêtes qui doivent réussir ensemble.

Préparation

CREATE TABLE client (
    num INT PRIMARY KEY,
    nom VARCHAR(50),
    prenom VARCHAR(50),
    adr VARCHAR(100),
    tel VARCHAR(20)
) ENGINE = InnoDB;

CREATE TABLE compte (
    num INT PRIMARY KEY,
    solde DECIMAL(10,2),
    type CHAR(2),
    num_client INT,
    FOREIGN KEY (num_client) REFERENCES client(num)
) ENGINE = InnoDB;

CREATE TABLE operations (
    num INT AUTO_INCREMENT PRIMARY KEY,
    type VARCHAR(20),
    montant DECIMAL(10,2),
    num_compte INT,
    date_o DATE,
    FOREIGN KEY (num_compte) REFERENCES compte(num)
) ENGINE = InnoDB;

INSERT INTO client VALUES (1, 'Alaoui', 'Amine', 'Rabat', '0600000001');
INSERT INTO client VALUES (2, 'Benani', 'Salma', 'Skhirat', '0600000002');

INSERT INTO compte VALUES (101, 1000, 'CC', 1);
INSERT INTO compte VALUES (102, 500, 'CE', 2);

Cas 1 : tout se passe bien, on valide

Virement de 200 DH du compte 101 vers le compte 102 :

START TRANSACTION;

-- débiter le compte 101
UPDATE compte SET solde = solde - 200 WHERE num = 101;
-- créditer le compte 102
UPDATE compte SET solde = solde + 200 WHERE num = 102;

-- enregistrer les 2 opérations : retrait puis versement
INSERT INTO operations (type, montant, num_compte, date_o) VALUES ('retrait', 200, 101, CURDATE());
INSERT INTO operations (type, montant, num_compte, date_o) VALUES ('versement', 200, 102, CURDATE());

-- valider
COMMIT;

-- résultat attendu : compte 101 = 800, compte 102 = 700
SELECT * FROM compte;
-- résultat attendu : 2 lignes d'opérations
SELECT * FROM operations;

Cas 2 : un problème survient, on annule

START TRANSACTION;

-- débit réussi
UPDATE compte SET solde = solde - 200 WHERE num = 101;
INSERT INTO operations (type, montant, num_compte, date_o) VALUES ('retrait', 200, 101, CURDATE());
-- le crédit du compte 102 échoue...

-- tout est annulé : le solde et l'opération
ROLLBACK;

-- résultat attendu : les soldes n'ont pas changé
SELECT * FROM compte;
-- résultat attendu : aucune nouvelle opération
SELECT * FROM operations;

6. Démo : le temps gagné avec autocommit = 0

Avec l'autocommit activé, chaque INSERT est validé, donc écrit sur le disque, un par un. Avec autocommit = 0, une seule validation a lieu à la fin, au COMMIT. Mesurons la différence.

Pourquoi pas 1000 lignes en lots de 100 ? Un INSERT de 100 lignes ne fait qu'une validation. Avec 10 lots il n'y a que 10 validations : l'écart est trop petit pour être visible. Il faut beaucoup d'INSERT d'une seule ligne.

La table et la procédure de test

CREATE TABLE test_insert (
    id INT AUTO_INCREMENT PRIMARY KEY,
    valeur VARCHAR(30)
) ENGINE = InnoDB;

DELIMITER $$
CREATE PROCEDURE test_commit(IN n INT, IN auto TINYINT)
BEGIN
    DECLARE i INT DEFAULT 1;
    DECLARE v_debut DATETIME(6);

    -- TRUNCATE valide tout seul : on le fait avant de lancer le chronomètre
    TRUNCATE TABLE test_insert;
    SET autocommit = auto;
    SET v_debut = SYSDATE(6);

    WHILE i <= n DO
        INSERT INTO test_insert (valeur) VALUES (CONCAT('ligne ', i));
        SET i = i + 1;
    END WHILE;

    -- le COMMIT fait partie du temps mesuré
    COMMIT;

    SELECT n AS lignes,
           auto AS autocommit,
           TIMESTAMPDIFF(MICROSECOND, v_debut, SYSDATE(6)) / 1000000 AS secondes;

    SET autocommit = 1;
END$$
DELIMITER ;

La procédure affiche une seule ligne : le temps global, pas celui de chaque requête.

Lancer les deux tests

-- test 1 : autocommit activé (10 000 validations)
CALL test_commit(10000, 1);

-- test 2 : autocommit désactivé (1 seule validation)
CALL test_commit(10000, 0);

Résultats à noter

TestautocommitNombre de validationsTemps (secondes)
1110 000
201
Conclusion : moins il y a de validations, plus l'insertion est rapide. Pour de gros volumes, on regroupe les requêtes dans une transaction.

Si l'écart est trop faible

Augmentez n (par exemple 50 000) et vérifiez ce réglage :

SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';

La valeur 1 force l'écriture sur le disque à chaque validation : c'est elle qui rend les validations coûteuses. Avec 0 ou 2, l'écart sera très réduit.

7. TP : transactions sur la base Glogiciels

Avant de commencer : les noms de colonnes ci-dessous (numproj, titreproj, codlog, nomlog, prixlog, numdev...) sont à adapter à votre script de la base Glogiciels.

Exercice 1 : annuler une insertion

Démarrez une transaction, insérez un nouveau projet, vérifiez avec un SELECT qu'il existe, puis annulez. Vérifiez qu'il a disparu.

Voir la solution 
START TRANSACTION;
INSERT INTO projet (numproj, titreproj) VALUES (10, 'Gestion de stock');
-- résultat attendu : 1 ligne
SELECT * FROM projet WHERE numproj = 10;
ROLLBACK;
-- résultat attendu : 0 ligne
SELECT * FROM projet WHERE numproj = 10;

Exercice 2 : valider une insertion

Refaites l'exercice 1 avec COMMIT à la place de ROLLBACK. Que constatez-vous ? Peut-on encore annuler ?

Voir la solution 
START TRANSACTION;
INSERT INTO projet (numproj, titreproj) VALUES (10, 'Gestion de stock');
COMMIT;
-- sans effet : la transaction est déjà terminée
ROLLBACK;
-- résultat attendu : la ligne existe toujours
SELECT * FROM projet WHERE numproj = 10;

Exercice 3 : modification annulée

Augmentez de 10 % le prix de tous les logiciels du projet 10, affichez les nouveaux prix, puis annulez et vérifiez que les anciens prix sont revenus.

Voir la solution 
START TRANSACTION;
UPDATE logiciel SET prixlog = prixlog * 1.10 WHERE numproj = 10;
SELECT codlog, nomlog, prixlog FROM logiciel WHERE numproj = 10;
ROLLBACK;
SELECT codlog, nomlog, prixlog FROM logiciel WHERE numproj = 10;

Exercice 4 : un bloc « tout ou rien »

Dans une même transaction : créez le projet 11, ajoutez-lui un logiciel, puis affectez le développeur 1 à ce projet. Validez.

Voir la solution 
START TRANSACTION;
INSERT INTO projet (numproj, titreproj) VALUES (11, 'Site e-commerce');
INSERT INTO logiciel (codlog, nomlog, prixlog, numproj) VALUES (101, 'ShopWeb', 2000, 11);
INSERT INTO realisation (numdev, numproj) VALUES (1, 11);
COMMIT;

Exercice 5 : une erreur au milieu

Refaites l'exercice 4 avec le projet 12, mais en affectant un développeur qui n'existe pas (ex. 999). MySQL refuse la dernière requête (clé étrangère). Que faut-il faire ? Vérifiez ensuite que le projet 12 et son logiciel n'existent pas.

Voir la solution 
START TRANSACTION;
INSERT INTO projet (numproj, titreproj) VALUES (12, 'Application RH');
INSERT INTO logiciel (codlog, nomlog, prixlog, numproj) VALUES (102, 'RHPlus', 1800, 12);
-- ERREUR
INSERT INTO realisation (numdev, numproj) VALUES (999, 12);
-- annule aussi les 2 premiers INSERT
ROLLBACK;
-- résultat attendu : 0 ligne
SELECT * FROM projet WHERE numproj = 12;

Exercice 6 : autocommit

Désactivez la validation automatique, supprimez un logiciel, annulez, puis réactivez l'autocommit.

Voir la solution 
SET autocommit = 0;
DELETE FROM logiciel WHERE codlog = 101;
-- le logiciel est de retour
ROLLBACK;
SET autocommit = 1;

Exercice 7 (bonus) : le virement dans une procédure

Créez la procédure virement(IN p_emetteur, IN p_recepteur, IN p_montant) sur la base de la banque : elle met à jour les 2 comptes et enregistre les 2 opérations. Si le solde de l'émetteur devient négatif, annulez la transaction. Sinon, validez.

Voir la solution 
DELIMITER $$
CREATE PROCEDURE virement(IN p_emetteur INT,
                          IN p_recepteur INT,
                          IN p_montant DECIMAL(10,2))
BEGIN
    DECLARE v_solde DECIMAL(10,2);

    START TRANSACTION;
    UPDATE compte SET solde = solde - p_montant WHERE num = p_emetteur;
    UPDATE compte SET solde = solde + p_montant WHERE num = p_recepteur;
    INSERT INTO operations (type, montant, num_compte, date_o)
        VALUES ('retrait', p_montant, p_emetteur, CURDATE());
    INSERT INTO operations (type, montant, num_compte, date_o)
        VALUES ('versement', p_montant, p_recepteur, CURDATE());

    SELECT solde INTO v_solde FROM compte WHERE num = p_emetteur;

    IF v_solde < 0 THEN
        ROLLBACK;
        SELECT 'Virement annulé : solde insuffisant' AS message;
    ELSE
        COMMIT;
        SELECT 'Virement effectué' AS message;
    END IF;
END$$
DELIMITER ;

CALL virement(101, 102, 200);

À retenir

  • MySQL valide chaque requête automatiquement (autocommit). Une transaction permet de grouper et d'annuler.
  • START TRANSACTION (ou BEGIN) : début. COMMIT : valider. ROLLBACK : annuler.
  • Transaction = « tout ou rien ». Exemple type : le virement bancaire.
