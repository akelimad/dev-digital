PARTIE 1 · THÉORIE

1. Qu'est-ce que le verrouillage des tables ?

Dans une base de données, plusieurs utilisateurs travaillent en même temps sur les mêmes tables. Sans règle, deux personnes peuvent modifier la même donnée au même moment et créer des erreurs.

Analogie : un document partagé. Avec un verrou READ, tout le monde peut le lire mais personne ne peut le modifier. Avec un verrou WRITE, une seule personne l'a en main : les autres attendent.

Verrouiller une table = réserver cette table pour ma session afin de contrôler ce que les autres sessions ont le droit d'y faire. Une session est une connexion ouverte à MySQL (par exemple une fenêtre CMD). Deux fenêtres CMD = deux sessions différentes, même avec le même utilisateur.

2. Syntaxe : comment verrouiller ?

LOCK TABLES nom_table READ | WRITE;     -- poser le verrou
UNLOCK TABLES;                          -- libérer tous les verrous
LOCK TABLES developpeur READ;
LOCK TABLES developpeur WRITE;

Une seule table ou plusieurs ?

On peut verrouiller plusieurs tables avec une seule instruction, séparées par des virgules, chacune avec son propre type de verrou :
LOCK TABLES developpeur READ, projet READ, logiciel WRITE;
Piège classique : deux LOCK TABLES successifs ne s'additionnent pas. Le second libère d'abord les verrous du premier.
LOCK TABLES developpeur READ;
LOCK TABLES projet READ;      -- developpeur n'est plus verrouillé !
Règle : une fois LOCK TABLES exécuté, la session ne peut utiliser que les tables verrouillées. Pour une jointure, il faut donc verrouiller toutes les tables de la requête (et les alias, par exemple projet AS p READ). Sinon : ERROR 1100: Table 'x' was not locked with LOCK TABLES.

Comment libérer : UNLOCK TABLES

UNLOCK TABLES;
Pas de nom de table. UNLOCK TABLES libère tous les verrous de la session d'un coup. On ne peut pas déverrouiller une seule table : UNLOCK TABLES developpeur n'existe pas.

TABLE et TABLES sont synonymes : LOCK TABLE et UNLOCK TABLE fonctionnent aussi. On écrit TABLES par convention.

Pour n'en libérer qu'une, on refait un LOCK TABLES avec seulement les tables à garder (il libère d'abord tous les anciens verrous) :

LOCK TABLES developpeur READ, projet WRITE;
-- je n'ai plus besoin de developpeur :
LOCK TABLES projet WRITE;     -- developpeur libérée, projet reverrouillée

4. Questions fréquentes et idées fausses

❓ Le verrou bloque-t-il toute la base de données ?

Non. Il ne concerne que les tables nommées dans LOCK TABLES. Les autres tables restent accessibles aux autres sessions.

❓ Un verrou READ empêche-t-il les autres de lire ?

Non. READ = tout le monde lit. Il bloque seulement les écritures (INSERT, UPDATE, DELETE).

❓ Mon propre verrou READ m'empêche-t-il d'écrire ?

Oui ! Avec READ, même moi je ne peux pas écrire : erreur 1099. Pour modifier, il faut un verrou WRITE.

❓ L'autre session reçoit-elle une erreur avec mon WRITE ?

Non, elle attend (la commande reste « figée ») jusqu'à mon UNLOCK TABLES. Une erreur de délai n'arrive qu'après un très long temps d'attente.

❓ Après LOCK TABLES, puis-je lire les autres tables ? Et les autres sessions ?

Ma session : non. Elle ne peut utiliser que les tables verrouillées (erreur 1100 sinon). Il faut tout verrouiller dès le départ.

Les autres sessions : oui. Elles peuvent lire et écrire librement dans les tables non verrouillées : mon verrou ne les concerne pas.

-- Session A
LOCK TABLES developpeur READ;
SELECT * FROM projet;        -- ❌ ERROR 1100 (projet non verrouillée pour A)

-- Session B (en même temps)
SELECT * FROM projet;        -- ✅ OK
UPDATE projet SET ...;       -- ✅ OK
SELECT * FROM developpeur;   -- ✅ OK (READ de A)
UPDATE developpeur SET ...;  -- ⏳ attend (READ de A)
❓ Quand le verrou est-il libéré ?

Par UNLOCK TABLES, par un nouveau LOCK TABLES, par START TRANSACTION, ou quand la connexion se ferme.

❓ Un autre utilisateur peut-il libérer mon verrou ?

Non. Le verrou appartient à ma session. Seule elle (ou sa fermeture, ou un KILL par l'administrateur) peut le libérer.

❓ Que se passe-t-il si j'oublie UNLOCK TABLES ?

Les autres sessions restent bloquées tant que ma connexion reste ouverte. Pensez toujours à libérer le verrou rapidement.

❓ Le verrouillage remplace-t-il les droits (GRANT) ?

Non. Le verrou règle les accès simultanés, pas qui a le droit d'accéder. Il faut en plus le privilège LOCK TABLES pour l'utiliser.

❓ Est-ce la meilleure méthode avec InnoDB ?

Pas toujours. Avec InnoDB, on préfère les transactions avec SELECT … FOR UPDATE (verrou sur des lignes, plus fin). LOCK TABLES reste utile pour comprendre le principe, pour MyISAM et pour la maintenance.

Scénario conseillé : ① A : LOCK … READ → testez les 4 actions dans A puis dans B. ② A : UNLOCK. ③ A : LOCK … WRITE → testez B (il reste bloqué). ④ A : UNLOCK → la commande de B s'exécute.
